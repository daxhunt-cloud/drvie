# T-001 · fix: delete-account 에서 comments 테이블 삭제 누락

> status: done · stage: phase3_complete · assignee: pdt-developer
> (mirrored header — PO updates mechanically on lifecycle change)

## Request

계정 삭제 API(`POST /api/delete-account`)가 DB 레코드를 정리하는 과정에서 `comments` 테이블 삭제를 누락하고 있다. 이로 인해 계정 삭제 후에도 해당 사용자가 작성한 댓글이 DB에 잔존하는 고아(orphan) 레코드가 누적된다. 감사 항목 **B-1** 에서 식별된 데이터 정합성 버그다. 삭제 대상은 "해당 사용자가 작성한 댓글"(`comments.user_id = userId`) 전체이며, 타인 코스에 달린 댓글도 포함한다.

## Approach

### 현황

`src/app/api/delete-account/route.ts:56-61` 의 DB 삭제 순서:

```
likes → bookmarks(user) → bookmarks(target) → courses → profiles
```

`comments` 테이블이 누락돼 있다. `comments`는 `course_id`(코스 FK)와 `user_id`(프로필 FK)를 보유한다.

---

### 옵션 비교

| | **Option A — API Route 1줄 추가 (권장)** | **Option B — FK ON DELETE CASCADE** |
|---|---|---|
| 변경 범위 | `delete-account/route.ts` 1줄 | Supabase 마이그레이션 SQL 2줄 (`comments.user_id`, `comments.course_id` 양쪽 CASCADE) |
| 즉시 적용 | ✅ 배포 즉시 | ❌ DB 마이그레이션 실행 필요 |
| 완전성 | `user_id = userId` 댓글만 처리 (충분) | 계정 삭제 + 코스 삭제 모두 자동화 |
| 롤백 | Git revert 1커밋 | CASCADE 제거 마이그레이션 필요 |
| 복잡도 | 없음 | 마이그레이션 + 기존 FK 정의 파악 필요 |

---

### 권장안: Option A

**이유**: 즉각 수정 가능하고 이미 API Route가 순차 삭제 패턴으로 동작 중이다. FK CASCADE는 별도 마이그레이션 심사가 필요하며 현재 스키마 정의 파일이 없어 기존 FK 구성 파악이 우선 필요하다. Option B는 향후 스키마 문서화 후 별도 P2 티켓으로 진행.

**수정 위치**: `src/app/api/delete-account/route.ts:57` — `likes` 삭제 직후, `courses` 삭제 전에 삽입.

**수정 전 (`lines 56-61`)**:
```ts
// 3. DB 데이터 삭제 (FK 순서: likes → bookmarks → courses → profiles)
await supabase.from("likes").delete().eq("user_id", userId);
await supabase.from("bookmarks").delete().eq("user_id", userId);
await supabase.from("bookmarks").delete().eq("target_user_id", userId);
await supabase.from("courses").delete().eq("user_id", userId);
await supabase.from("profiles").delete().eq("id", userId);
```

**수정 후**:
```ts
// 3. DB 데이터 삭제 (FK 순서: likes → comments → bookmarks → courses → profiles)
await supabase.from("likes").delete().eq("user_id", userId);
await supabase.from("comments").delete().eq("user_id", userId); // ← 추가
await supabase.from("bookmarks").delete().eq("user_id", userId);
await supabase.from("bookmarks").delete().eq("target_user_id", userId);
await supabase.from("courses").delete().eq("user_id", userId);
await supabase.from("profiles").delete().eq("id", userId);
```

주석의 FK 순서 설명도 `comments` 포함으로 업데이트.

**주의**: 타인 코스에 달린 내 댓글은 `courses.delete()` 이후 orphan이 되므로 반드시 `courses` 삭제 이전에 처리해야 한다.

## Acceptance

- [ ] 계정 삭제 API 성공 응답(`{ ok: true }`) 후, 해당 `userId`로 `SELECT * FROM comments WHERE user_id = '<userId>'` 결과가 **0건**인 것을 Supabase SQL Editor에서 확인
- [ ] 타인의 코스에 댓글을 달고 계정 삭제 시, 해당 댓글도 삭제되는 것을 확인
- [ ] 자신의 코스에 달린 타인의 댓글은 삭제되지 **않는** 것을 확인 (본 티켓 범위 외)
- [ ] 계정 삭제 후 `profiles`, `likes`, `bookmarks`, `courses` 도 기존대로 정상 삭제되는 것을 함께 확인 (회귀 방지)
- [ ] 오류 없이 빌드 통과 (`npx tsc --noEmit`)

## Out of scope

- `comments.course_id` FK CASCADE 설정 (코스 삭제 시 댓글 자동 삭제) — 별도 스키마 마이그레이션 티켓으로 분리
- `comments.user_id` FK CASCADE 설정 — 동일
- 타인이 내 코스에 달한 댓글의 처리 방침 결정 — 정책 결정 필요, 현재는 코스와 함께 남겨둠
- 댓글 소프트 삭제 — 별도 P2 범위

## Notes / risks

- **마이그레이션 없음**: 코드 변경만으로 해결. Supabase Dashboard SQL 실행 불필요.
- **기존 고아 레코드**: 이미 DB에 잔존 중인 orphan comments는 별도 일회성 정리 SQL 필요 (`DELETE FROM comments WHERE user_id NOT IN (SELECT id FROM profiles)`). 본 티켓은 신규 발생 방지만 담당.
- **롤백**: Git revert 1커밋으로 즉시 복구 가능.
- **레이트 리밋**: 기존 3/min 유지. 변경 없음.
